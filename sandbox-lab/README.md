# 沙盒试验台（research/sandbox-lab）

研究用，**不继承主项目**：单文件、零依赖、不进 `src/` 也不进 `public/`，`pnpm run build` 与 `tsc` 都不碰它。
要解决的问题只有一个：

> 手头有几篇文章，外面来了一堆修改指令。指令要能**预览**、能**执行**、能**放弃**、能**恢复**。

## 怎么跑

```bash
# 直接看
open sandbox-lab/index.html          # 手机上也能开，单文件

# 语义自检（37 项，需要本机 playwright + chromium）
node sandbox-lab/selfcheck.mjs
```

## 三份状态，四个动作

```
docs         已提交的文章（唯一真相，只有执行/恢复会改它）
instructions 指令队列：{op, target, find, to, text, status}
history      快照链：{seq, label, kind, docs, ids}
```

`pass(docs, ids)` 是纯函数：在 `docs` 的深拷贝上按队列顺序跑一遍，返回
`{docs, steps, notes, changedDocs}`，**全程不碰 `docs`**。

| 动作 | 做什么 | 改 docs？ | 产生快照？ | 可否撤销 |
| --- | --- | --- | --- | --- |
| 预览 | 整条流水线重算，出逐条 diff + 整体 diff | 否 | 否 | 无所谓 |
| 执行 | 把预览算出的内容落成新版本，成功的指令标 `applied` | 是 | 是（`commit`） | 可（恢复） |
| 放弃 | 只把指令状态改 `discarded` | 否 | 否 | 可（找回） |
| 恢复 | 先存「恢复前的现场」，再把目标快照内容切回来 | 是 | 是（`checkpoint` + `restore`） | 可（再恢复） |

指令状态机：`pending → needs（跑不通，留原因） → applied（已提交） / discarded（已放弃）`，
`needs` 和 `discarded` 都能回到 `pending`。

## 研究结论（六条）

1. **预览必须是纯函数，且不能缓存单条结果。** 指令之间互相喂内容：`i6` 要改的「小柚」是 `i5` 造出来的。
   自检里专门测这条——把 `i6` 挪到 `i5` 前面，预览失败数从 1 变 2；挪回去又变回 1。
   所以「顺序」是指令队列的数据之一，界面上给了 ↑↓，重排即作废上一轮的 `需复核` 判定。

2. **拒绝整条，绝不部分写入。** 一条指令内部（比如 `replace` 找不到原文）失败，就整条不进，
   留 `err` 给人看；批量执行时其它指令照常提交，坏指令留在队列里，不因为一条把整批卡死。
   单条坏指令执行时**连快照都不产生**（自检第 9 项验证：`snaps` 和 `docHash` 都不动）。

3. **「放弃」和「恢复」是两件事，别混。** 放弃动的是**指令**（内容一个字节没变，`docHash` 不变）；
   恢复动的是**内容**（指令状态跟着回滚）。两者都可逆：放弃了能找回，恢复了能再恢复回去。

4. **恢复用 append-only，不抹历史。** 恢复时先把当前内容存成 `checkpoint` 快照，再落一条 `restore` 快照。
   这样「回滚」本身还能撤销，历史链永远只增。同时把目标版本自带的那批指令标回 `applied`，
   否则恢复后它们又变成待执行，会被重复跑一遍（自检第 8 项两头都测了）。

5. **逐条 diff 和整体 diff 会不一样，这是对的。** 逐条用 stepwise 的中间态算，整体用 `head → final` 算。
   `i5` 的逐条 diff 显示「她 → 小柚」，整体 diff 里那行却是「她 → 柚子」，因为后面还有 `i6`。
   给人看的应该是整体 diff，逐条只用来回答「这条指令到底干了什么」。

6. **diff 粒度取行级 LCS，标题当第 0 行参与 diff。** 文章本来就是段落式的，行级足够；
   标题跟着进 diff 才能一眼看出 `rename` 指令的作用，否则改标题在预览里是隐形的。

## 已知边界 / 下一步

- 快照是**全量深拷贝**。文章几十篇、每篇几千字时内存会难看。下一步：快照只存 `op log + 版本号`，
  需要时重放；或者按文章分片存快照（一篇文章一条链）。
- 冲突检测只有「找不到原文」。真正的语义冲突（两条指令改同一行、`append` 与 `replace` 打架）还没做，
  需要行区间重叠检测 + 冲突时强制人工排序。
- 没有「删除文章」这类指令，因为它会牵出「恢复时文章要不要回来、它的 id 能不能复用」。
- 没有并发。接进主项目时这是第一个坑：同一篇文章在两个端上各跑一批指令，合并策略得先定。

## 若要接进 DatingRecord

映射关系是现成的：`docs` → 文章的正文/标题字段，`instructions` → 一张指令表（带 status/err/顺序号），
`history` → 快照表。`pass()` / `diffLines()` 可以直接搬过去用（纯函数，无 DOM 依赖）。
需要额外补的：写库时的事务边界（一次执行 = 一个事务）、SW 缓存失效、以及上面那条并发合并策略。

# 沙盒试验台（research/sandbox-lab）

研究用，**不继承主项目**：单文件、零依赖、不进 `src/` 也不进 `public/`，`pnpm run build` 与 `tsc` 都不碰它。

要解决的问题：

> 手头有几篇文章，外面来了一堆修改指令。先把指令**打包成指令集**，再对整个集做四件事：
> **预览**（只看有增/删/改的文章）、**执行**、**回退**、**放弃**。

## 怎么跑

```bash
open sandbox-lab/index.html        # 单文件，手机上也能直接打开
node sandbox-lab/selfcheck.mjs     # 38 项语义自检（需要本机 playwright + chromium）
```

## 状态与生命周期

```
docs         已提交的文章（唯一真相，只有执行/回退会改它）
instructions 指令定义池（op / target / find / to / text）
sets         指令集：{name, ids[], status, commitSeq, baseSeq, applied[], failed[]}
history      版本快照：{seq, label, kind: seed|commit|revert, docs, setId}
```

指令集一生：

```
        打包                执行                回退
池 ──────────▶ draft ──────────▶ committed ──────────▶ reverted ──┐
                  │                                                │ 整集退回池子
                  │ 放弃                                           ▼
                  ▼                                              池
              discarded ──── 指令立即回池，记录可删除
```

| 动作 | 改内容 | 产生版本 | 适用状态 | 可逆方式 |
| --- | --- | --- | --- | --- |
| 预览 | 否 | 否 | draft | — |
| 执行 | 是 | 是（`commit`） | draft | 回退 |
| 回退 | 是 | 是（`revert`） | committed | 整集退回池子后重新执行 |
| 放弃 | 否 | 否 | draft | 指令自动回池，重新打包 |

**执行与回退成对**：底部按钮在集为草稿时显示「执行」，一旦该集已执行就原地变「回退」；
已执行的集不给「放弃」——它已经改了内容，唯一的出路是把内容退回去。

## 预览只显示增删改

`classify(before, after)` 把结果分成三类：**增**（集里有 `create`）、**改**（标题或正文变了）、**删**（文章被 `delete`）。
没被碰到的文章不进预览，只给一行计数：`影响 3 篇：增 1 / 改 1 / 删 1；1 篇未受影响，已隐藏`。
三篇里改一篇时不会被两篇无关内容刷屏，这是「预览」这个动作唯一该回答的问题。

## 研究结论（八条）

1. **最小事务单位是「指令集」，不是单条指令。** 单条指令没有「成功」可言：它改的是同一批文章，
   A 的产物是 B 的输入。所以池子只负责攒料，打包之后才谈预览、执行、回退、放弃。

2. **预览必须是纯函数，且整条流水线重算。** 集内顺序影响结果：`p6` 要改的「小柚」是 `p5` 造出来的，
   把 `p6` 挪到 `p5` 前面，预览失败数就从 1 变 2；挪回去又变回 1（自检第 9 组）。
   所以顺序是数据的一部分，集内给了 ↑↓，重排即作废上一轮的失败判定。

3. **预览不能消耗任何计数器。** 第一版给新建文章分配 id 用全局 `++docSeq`，结果点一次预览就多占一个号，
   预览后执行出来的文章 id 和预览里看到的不是同一个。改成由指令 id 决定（`'n' + i.id`），
   预览多少次结果都一样。**幂等性是预览的前提。**

4. **回退按后进先出。** 集 B 依赖集 A 的产物时，直接回退 A 会让 B 的结果失去前提。
   所以只允许回退「最晚的那个已执行集」，否则拒绝并指名道姓（自检第 6 组）。
   代价是回退栈必须是栈；好处是不用处理「中间抽走一层」的合并语义。真要做，得先有逐行三方合并。

5. **回退是新增一条 `revert` 版本，不是抹掉 `commit`。** 历史只增不删，所以「回退」本身也能被回退，
   出问题时有现场可查。

6. **坏指令整条拒绝，但不连坐。** 集里 `p7` 找不到原文，执行时它不进（留在集里标「跑不通」+ 原因），
   其余指令照常提交成一个版本；**全跑不通的集则一条都不提交、不产生版本**，保持草稿。
   集还提供「移出跑不通的」，一键把坏指令退回池子。

7. **「放弃」和「回退」是两件事。** 放弃动的是**指令集**（内容一个字节都没动，`docHash` 不变，指令立刻回池）；
   回退动的是**内容**。混在一起做就会出现「想撤销一条指令结果改了六篇文章」的事故。

8. **删除类指令要单独设计。** `delete` 之后，任何指向该文章的指令都会失败（原因要写成「可能已被前面的指令删掉」
   而不是「目标不存在」）；回退时它要能完整回来——靠的就是第 5 条的全量快照，不需要额外的「反删除」指令。

## 已知边界 / 下一步

- 快照是全量深拷贝。文章几十篇、每篇几千字时会难看：改成 op log + 重放，或按文章分片各存一条链。
- 冲突只到「找不到原文」这一层。两条指令改同一行的语义冲突、以及非栈式回退，都需要逐行三方合并。
- 集与集之间目前只有顺序关系，没有依赖声明（A 集标注「我依赖 B 集」），LIFO 是隐式约定而非显式检查。
- 没有并发。接进主项目时这是第一个坑：同一批文章在两个端上各打包各执行，合并策略得先定。
